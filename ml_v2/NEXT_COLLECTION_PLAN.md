# Proposed next collection: V2 fresh-task study

Status: planning only; no new collection jobs or resource requests submitted.

1. Inventory candidates. Confirm the original research manifest and source snapshot hashes. Count unused, usable candidates by family, source and natural input length. Apply the existing exact/related-group exclusion machinery against every original training/calibration/confirmation assignment, pilot and smoke task. A different task ID alone does not establish novelty.
2. Diagnose existing rare events. Review the pre-run inputs and trace patterns for the 30 training task groups with output-ceiling events. Distinguish long legitimate outputs, JSON formatting/truncation, repeated context reads and request-limit behavior. These are descriptive categories; label disagreements and uncertainty rather than assuming a single cause. Keep original quality checks and trace files unchanged.
3. Select a small integration pilot. A proposed 32 new groups, four per family, produce 128 model/seed attempts under the unchanged V1 policy. Keep these development-only. Its purpose is to verify novelty, schema, trace capture, and throughput; it is too small for reliable model/coverage claims. Do not select a pilot based on observed favorable outcomes.
4. Finalize research counts after inventory and throughput. Use targeted development enrichment for coding, ideation, tabular and naturally long summarization tasks. Reserve fresh calibration groups before fitting their correction and fresh final-test groups before any model selection. Predefine the evaluation family mixture and natural-length strata; report any risk-enriched stress test separately. If a balanced family test changes the family mix from V1, report standardized metrics using fixed V1 family weights as well as balanced-sample metrics.
5. Preserve meaningful repetition. All variants of a task stay together. V1 seed pairs had identical token totals, so repeating seeds is not evidence of independent task diversity. Maintain both declared seeds for a directly comparable study unless a change is justified and versioned before collection; report unique groups explicitly.
6. Maintain controller identity or version changes explicitly. A study of improved JSON enforcement, larger output caps or a different request limit needs separate configurations, pre-run policy features and a new estimand. It cannot be described as simply improving prediction for the unchanged V1 workload.
7. Fix promotion gates before final evaluation. Compare candidates against V1 on identical new task groups. Require a material MAE improvement without worse expensive-run underprediction, and a separately assessed budget-coverage/slack tradeoff. Do not pick an arbitrary numerical gain after seeing the test results. Use grouped uncertainty summaries and inspect minimum family coverage, while recognizing small-sample uncertainty and selective missingness.

The next external input needed is the Roar candidate/source inventory and access to its preparation/exclusion metadata. Existing local V1 artifacts do not contain the full unused candidate pool. A new collection's size and compute request should be set after that inventory and the integration pilot, not guessed from the prior token totals, which are not runtime or allocation cost.
